# pocket-law-code

個人開発やOSSで、別の人やエージェントが判断を続けられる変更を作るための
Agent Skillsです。適用先の契約と開発方法を調べ、必要な変更・検証・説明を選びます。
プロジェクト固有の規範は、上位指示・安全・実際の権限の範囲で優先します。
推測したニーズを、明示された要求より優先するための規約ではありません。

## 選ぶ

| Skill | 使う依頼 | 対象外 |
| --- | --- | --- |
| [pocket-change](skills/pocket-change/SKILL.md) | 契約・呼び出し元・検証方法の判断を伴う機能追加、不具合修正、リファクタリング | 機械的な置換、読むだけのレビュー |
| [pocket-review](skills/pocket-review/SKILL.md) | 提案されたコードや設定変更のレビュー | 通常の実装中の自己確認、依頼されていない全体監査 |
| [pocket-handoff](skills/pocket-handoff/SKILL.md) | 既存成果のPR説明、Issue更新文、再開のための引き継ぎ | 短い進捗返信、一般的な文章修正、引き継ぎを別途頼まれていない実装 |

必要なものだけ導入できます。他のSkill、専用ツール、元リポジトリへの接続は不要です。
通常の変更作業の完了報告は`pocket-change`に含まれます。
実装後に必ず他の2つを呼び出す仕組みではありません。

## 導入する

各配布物は、[Agent Skills仕様](https://agentskills.io/specification)の
`SKILL.md`だけで動くディレクトリです。本体の指示は英語で記述しています。
まず採用する版の差分を確認し、このリポジトリのcommitを控えてください。

Codexではプロジェクトの`.agents/skills/`に置けます。
個人用の置き場は`~/.agents/skills/`です。[Claude Code](https://code.claude.com/docs/en/skills)では通常
プロジェクトの`.claude/skills/`を使います。その他のホストでは、そのホストの
Skill探索先に同じディレクトリを置きます。
探索先はホストの仕様に依存します。Codexについては
[公式のSkillsガイド](https://learn.chatgpt.com/docs/build-skills)を参照してください。

このリポジトリのルートから、採用するSkillごとに実行します。
`target`を適用先に置き換え、`skill`を表の名前から選びます。

```sh
target="/path/to/project/.agents/skills"
skill="pocket-change"
mkdir -p "$target"
mkdir "$target/$skill" &&
  cp -R "skills/$skill/." "$target/$skill/"
```

同名のディレクトリやシンボリックリンクがあれば、`mkdir`が失敗しコピーしません。
途中でコピーが失敗した場合は、今回作ったディレクトリの内容を確認して片づけてから
再実行してください。同梱の`LICENSE`も配布先で保持してください。
プロジェクトで共有する場合は、Skillと採用元commitを導入の変更履歴に残します。

AGENTS、CI、依存、IssueやPRのテンプレートを変更する必要はありません。
導入は公開・投稿・マージ・デプロイの権限を追加しません。

## 使う

Skillの名前とdescriptionから、ホストが適用するものを選びます。
一覧に現れることと、適切に選ばれることは別なので、新しい会話で利用を確認してください。
Codexで一覧が更新されない場合は再起動します。
明示的に使う場合の例は次のとおりです。

```text
$pocket-change limit=0のエクスポートが空になる不具合を直して。
$pocket-review この差分を、互換性とデータへの影響を中心にレビューして。
$pocket-handoff 今の差分からPR説明の下書きを作って。投稿はしないで。
```

ホストごとの呼び出し構文が異なる場合は、その構文を使ってください。
Skill一覧を渡さないハーネスでは、必要な`SKILL.md`のパスを指定して使えます。
例えば「`.claude/skills/pocket-review/SKILL.md`を読んで、この差分をレビューして」と
依頼します。これはホストによる自動発見・選択の保証とは別です。
Skillを読み込めない場合は、読めたことにせず不足を伝えます。
プロジェクトの規範や依頼が十分に具体的なら、追加の手順を増やす必要はありません。

## 更新・削除する

更新するSkillの新旧を比較し、適用先での修正がないか確認します。
既存のディレクトリを探索先の外へ退避してから、新しい版を上の手順で置きます。
更新後に新しい会話で確認し、問題があれば退避した版へ戻します。
自動更新や、作業中のエージェントに読ませたままの差し替えは行いません。

削除する場合は、導入したSkillのディレクトリだけを探索先から取り除きます。
共用のskillsディレクトリやプロジェクトの規範は削除しません。
同じ名前を個人用とプロジェクト用の両方に置くことは避けてください。

## 検証・改善する

[evals](evals/README.md)に、発見、修正、読み取り専用レビュー、ローカル規範との競合、
不要な適用を調べる合成ケースがあります。実際の選択、操作、差分、引き渡しを観察し、
Skillなしの実行と比較します。形式検査だけでは判断品質の改善を証明できません。

変更するときは、失敗した場面と受け手への影響を先に確かめます。
説明を増やす前に、descriptionの適用条件、責務の重複、不要な指示を見直してください。
