# Hand over a decision someone can continue

Use the project's contracts and contribution rules within the governing
instruction hierarchy, safety constraints, and granted permissions. This skill
fills gaps; it neither replaces project policy nor grants authority. Treat
inferred needs as hypotheses, not additional requirements.

## Reconstruct only what the reader needs

Identify the recipient, what they must decide or do, and the requested destination
and format. Inspect the actual work, relevant local instructions or templates,
and available validation records. Do not rely on conversation history alone.

Distinguish the requested goal, the implemented behavior, decisions actually
made, and hypotheses still open. Preserve the author's attribution: do not
invent user motives, agreement, approval, or human understanding. If local rules
reserve part of a document for a human, leave that part clearly for them and
complete the parts you can draft.

When implementation and a maintained contract disagree, distinguish a proposed
contract change from one already agreed. Flag the unresolved decision rather
than assuming which source must be rewritten.

Tie each verification claim to the work and environment it actually covers.
Earlier revisions, suggested commands, and unexecuted checks are not evidence
that the current result passes. If verification is unavailable, state the gap
and a practical way to close it; do not invent results to finish the narrative.

## Make the next action possible

Explain the problem and resulting behavior before implementation detail. Include
the reason for material choices, affected contracts or compatibility, evidence
and its limits, and remaining work only as needed for the recipient's decision.
For resumption, include the current state and the next concrete action. Scale
detail to the work; omit empty headings, command diaries, and repeated facts.

When updating durable records is within the requested scope, put constraints
where the project maintains them; otherwise identify needed updates in the draft.
Link existing details rather than copying them into several records. Do not
declare every document authoritative, demote all specifications to stale notes, or create an
issue, ADR, changelog entry, or new process merely to satisfy this skill.

Use the requested medium and existing template. When none exists, short prose
covering outcome, rationale, evidence, and open decisions is enough. Do not force
a universal PR or issue template onto another project.

## Deliver within the requested authority

Check that a reader without the conversation can distinguish what is done,
what is known, and what needs their action. Remove claims not supported by the
actual work. Keep sensitive or unrelated information out of the handoff.

Drafting does not authorize sending, publishing, approving, merging, or deploying.
If the user already authorized a particular delivery action, complete it within
that scope and the project's rules; otherwise provide the prepared artifact.
